# Schema drift: `alembic upgrade head` vs `app/models.py`

**RESOLVED as of t_e7fbfe21 (2026-10-01), branch `dev/t_e7fbfe21-schema-drift`.**
Measured drift is now **zero**. The analysis below is kept because it explains
why the drift existed and what the remaining caveats are.

## Decision: bring the chain up to the model

Two revisions were added, both additive:

| revision | what it does |
|---|---|
| `20261001_model_tables_parity` | creates the 14 tables no migration created |
| `20261001_model_columns_parity` | adds the ~46 missing columns across 11 tables, and moves `admin_auth`'s PK from `admin_phone` to `id` |

Option 2 ("migrations are archival, build clean schemas some other way") was
rejected. `Base.metadata.create_all` in `app/main.py`'s lifespan creates
tables but seeds no rows, so it cannot express seed data (countries, trigger
weights, plans), and it is a side effect of booting the app — nothing verifies
it. `alembic upgrade head` on a clean database is what CI needs, and it now
produces a working schema.

## The worst finding was not in the card: admin auth was dead

The card described `plans.price_per_gb` as the drift's visible symptom. The
more serious one was `admin_auth`, which on a migrated database had **no
`email` and no `password_hash` column at all** and was keyed by
`admin_phone VARCHAR(20) NOT NULL` PRIMARY KEY.

`app/routers/auth.py` and `app/routers/superadmin.py` filter admins by
`AdminAuth.email` in 19 places, and every admin is created with `email=` and
`password_hash=` and never with `admin_phone=`:

```python
app/routers/auth.py:369        AdminAuth(email=email, password_hash=password_hash, ...)
app/routers/superadmin.py:217  AdminAuth(email=..., password_hash=..., role=...)
```

So on a clean build **every admin login raised `UndefinedColumnError: column
admin_auth.email does not exist`, and admin creation would fail the NOT NULL
constraint on `admin_phone`**. This was invisible because production was grown
by `create_all`, which had the columns.

`20261001_model_columns_parity` moves the PK to the `id` UUID the model
declares and makes `admin_phone` nullable. Safe: no foreign key anywhere
references `admin_auth` (verified against `information_schema`), and the one
legacy PIN-login path (`auth.py:483`) only filters on `admin_phone`.

Verified end-to-end on a pure migration build — insert as the superadmin
router does, read back as the login path does, bcrypt verify both ways.

## What now guards this

| guard | what it does |
|---|---|
| `backend/tests/test_schema_parity.py` | 4 tests: every model table and column exists in the migrated schema, plus the two concrete breakages (`admin_auth.email`, `plans.price_per_gb`). Negative control verified: all 4 fail against a database built without the parity revisions. |
| `scripts/schema_drift_report.py` | now exits non-zero on drift (was always 0), so it is a gate rather than a reading. |
| CI step `Check schema parity` | runs the report against the migrated database right after `alembic upgrade head`. |

Both the test and the report compare columns **case-insensitively**: Postgres
folds unquoted identifiers to lower case, so the model's
`referral_credits.credit_amount_nGN` is legitimately stored as
`credit_amount_ngn`. A case-sensitive comparison reports that as missing
forever and trains people to ignore the gate.

## Remaining caveats (deliberately not fixed here)

  * **Reverse drift is untouched.** The migrated schema has tables and columns
    the model does not declare (`dante_users`, `consent_events`,
    `referral_abuse_events`, `dante_port`, `alert_sent_*_pct_at`,
    `bunche_credential_id`, `charon_escalations.initial_message`). Dropping
    live columns to satisfy an autogenerated diff is destructive and out of
    scope. `alembic revision --autogenerate` proposes all of it; its output is
    far too noisy to apply unreviewed.
  * **`001_initial` is not idempotent.** Running `alembic upgrade head` over a
    schema built by `create_all` fails at `001` with
    `DuplicateTableError: relation "customers" already exists`. The two parity
    revisions *are* idempotent (verified over a `create_all`-shaped schema);
    the older ones are not. Out of scope here.
  * **Production is untouched.** Frozen at `merge_20260819_three_heads`. These
    revisions are additive and only affect databases that run the chain.

## Original analysis (t_2af95a6b, branch `devops/ci-gate-t_2af95a6b`)

**Status as of t_2af95a6b (2026-10-01), branch `devops/ci-gate-t_2af95a6b`,
re-verified against `main` @ 01ec239b.**

## The short version

`alembic upgrade head` now succeeds on a clean Postgres 16 (exit 0, 29 upgrade
steps across a 31-revision chain, single head) after nine defects were fixed.
But reaching `head` is not the same as producing the schema the application
expects. The migration chain and `app/models.py` still disagree substantially:
14 model tables are never created, and 11 more are missing columns.

That disagreement is currently **latent rather than visible** — the one code
path that read the missing columns (`/api/products`) was deleted by
`t_6edcf426`, which removed the symptom without touching the cause. Treat the
numbers below as a live landmine, not a closed issue.

This document records the gap so it is not rediscovered from scratch. It is
**not** fixed here — closing it is a separate, larger piece of work.

## Why the two disagree

This is not random drift. It is structural:

- `app/models.py` is the authoritative schema. Production was grown by hand
  and by `Base.metadata.create_all` at application startup.
- `alembic/versions/` was written largely *after the fact*, as a historical
  record. `008_add_admin_role` says so explicitly: its changes "were applied
  directly to production Postgres ... this migration exists purely to record
  that in version history."
- Several migrations were written against an **older** model than the one
  deployed (that is why `20260827_missing_indexes` asked to index
  `orders.customer_id`, a column that never existed in either).

So the chain is a record of production, not a recipe for building production.
That is workable, but it means a clean `alembic upgrade head` will never by
itself produce a working schema until the missing DDL is written down.

## What this breaks

`plans.price_per_gb` and its siblings are why `/api/products` could not work
against a migrated database. It selected the full `Plan` model and the migrated
table does not have those columns:

```
UndefinedColumnError: column plans.price_per_gb does not exist
```

That is not an assertion mismatch — it is a hard query failure, and it was one
of the reasons three `tests/test_routers_products.py` tests were red.

**As of `main` @ 01ec239b this specific breakage is gone, but not because the
drift was fixed.** Card `t_6edcf426` deleted the dead `/api/products` route
outright, along with its test file. The `plans` drift is still there in the
table list above; nothing reads those columns yet, which is why it is latent
rather than visible.

The endpoint was independently dead: it returned `{"products": []}` in
production and nothing in the frontend called it — the storefront uses
`/api/catalog`, which is live and serves 33 enabled plans. So the drift and the
dead endpoint were two separate problems that happened to overlap.

**This is the important part for whoever picks up the drift:** deleting the
consumer hid the symptom. Any future code that selects `Plan` columns
(`price_per_gb`, `min_gb`, `max_gb`, `gb_tiers`, `rotation_mode`,
`static_price_multiplier`, `supports_city`, `supports_country_change`) against
a database built by `alembic upgrade head` will hit the same
`UndefinedColumnError`. The storefront's `/api/catalog` is the thing to check
against the `Plan` model before trusting it on a clean build.

## What was fixed in t_2af95a6b

Nine defects that made `alembic upgrade head` fail on a clean database:

| revision | defect |
|---|---|
| 001 | `orders` declares an FK to `bunche_credentials` before that table exists — and the two tables reference each other, so reordering cannot fix it. FK moved to a deferred `create_foreign_key`. |
| 001 | `alembic_version.version_num` is `varchar(32)` but two revision ids are longer (`003_add_admin_invites_feature_flags` is 35) — stamping them raised `StringDataRightTruncationError`. Column widened to 64. |
| 009 | `ALTER TABLE admin_audit_log` on a table **no migration ever created**. `001` creates `customer_audit_log`; `admin_audit_log` exists only in the model and in production. Now created (guarded) in 009. |
| 010 | Renamed `bun_password`, but `001` creates that column as `password_hash`. Raised `UndefinedColumnError`. Both source names now handled. |
| 019 | `ADD COLUMN` on three columns `001` already creates. The inline comment claimed "Postgres ignores no-op ALTER" — it does not. Now `IF NOT EXISTS`. |
| 021 | `op.create_index(..., postgresql_only=True)` — not a valid SQLAlchemy argument. Raised `ArgumentError` before emitting any SQL. Removed. |
| 20260809_rls | Policies joined `orders.id`, but `orders`' PK is `order_id`. Raised `UndefinedColumnError`. Corrected. |
| 20260809_referral | A batch of six `COMMENT ON` statements in one `execute()`. asyncpg rejects that: "cannot insert multiple commands into a prepared statement". Split. |
| 20260827_missing_indexes | Indexed `orders.customer_id` and `styxproxy_credentials.customer_id`, which exist in neither the model nor `001` (the model uses `customer_phone`). Also indexed `tx_ref`, which no migration creates. Corrected, and index creation is now skipped when the column is absent. |

## Two more defects outside the migration chain

Both were found while verifying the above, and both had been invisible for the
same reason the tests were: `continue-on-error` on the job.

1. **`pip install -e ".[dev]"` failed outright.** No `[tool.setuptools]` section
   meant flat-layout auto-discovery found eight top-level packages under
   `backend/` and hard-failed the build. The step that installs the
   dependencies the tests need was failing on every run.
2. **`pyjwt` was undeclared.** `app/services/ops_auth.py:6` does `import jwt`,
   which is PyJWT — a different distribution from the declared
   `python-jose` (whose module is `jose`). On a clean install, 15 test modules
   died at import with `ModuleNotFoundError: No module named 'jwt'`.

Together these mean the backend-test job was not merely tolerant of failure;
it could not have run the suite successfully at all. Fixing them is a
precondition for the gate in `ci.yml` meaning anything.

## What is left to do

Closing the drift itself is **not** in t_2af95a6b and is not a CI-config
change. It needs a decision that is not the devops caller's to make:

1. Decide the source of truth going forward — either bring the migration chain
   up to the model (write the missing DDL as new revisions, which is the
   safer default because it does not touch production), or accept that
   migrations are a historical record only and generate a clean schema some
   other way.
2. Treat the deleted `/api/products` route as a warning, not a fix. Its test
   file is gone and the CI baseline entries are gone with it, so nothing in CI
   exercises those `Plan` columns any more. The drift is still real; the
   symptom just lost its only witness.

Until then, the `20260827_missing_indexes` guards make the chain tolerant: it
skips an index whose column is absent and prints what it skipped, rather than
aborting the whole migration.
